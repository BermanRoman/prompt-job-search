# Локальная проверка полноты карточек

[company_screen.py](../scripts/company_screen.py) принимает уже осмысленные декларации проверок компании и проверяет только их полноту, формат и срок доказательств.

Он не обращается к сети, не интерпретирует сырой ответ Checko и не устанавливает истинность деклараций, применимость источника, отсутствие трудовых нарушений, наличие бюджета или полномочия на отправку.

Проверка дополняет [поиск компаний](../company-discovery.md) и [карточку компании](../templates/company.md), независимая содержательная проверка остаётся обязательной по campaign.md.

## Запуск

Требуется Python 3.9 или новее, дополнительных пакетов нет.

```sh
python3 scripts/company_screen.py --input /private/campaign/cards.json --output /private/campaign/api-screen.json --stage api
python3 scripts/company_screen.py --input /private/campaign/cards.json --output /private/campaign/final-screen.json --stage final
python3 scripts/company_screen.py --input /private/campaign/cards.json --output /private/campaign/example-screen.json --stage final --now 2030-01-01T12:00:00Z
python3 -m unittest discover -s tests -p test_company_screen.py -v
```

`--now` задаёт контрольное время для воспроизводимой проверки, по умолчанию используется текущее UTC.

Подмена текущего времени историческим не даёт допуска к действию сегодня, перед отправкой проверяй фактическую актуальность.

Вход и выход хранятся вне публичного репозитория либо внутри игнорируемого `runs/`, расположение проверяется после разрешения символических ссылок.

Родительский каталог результата должен уже существовать, новый файл создаётся исключительно с правами `0600`, существующий файл или символическая ссылка не перезаписываются.

В stdout выводятся только число компаний и счётчики решений, подробности находятся в закрытом JSON-файле.

Код выхода 0 означает успешную проверку и запись отчёта, даже если все решения — `exclude` или `unknown`, код 2 означает ошибку формата или хранения без отчёта об успехе.

## Схема входа

Учебный пример одной декларации, остальные проверки намеренно отсутствуют, поэтому итог будет `unknown`.

```json
{
  "companies": [
    {
      "company_id": "synthetic-company",
      "checks": {
        "identity": {
          "status": "pass",
          "evidence": [
            {
              "source": "snapshot:synthetic/identity-1",
              "scope": "Учебное сопоставление сайта и юридического лица по реквизитам",
              "checked_at": "2030-01-01T11:00:00Z",
              "valid_until": "2030-01-01T13:00:00Z"
            }
          ]
        }
      }
    }
  ]
}
```

Допустимы только показанные поля, дополнительные поля на любом уровне отклоняются, полная карточка с заметками и первичные ответы сервисов хранятся отдельно.

Корень содержит список `companies`, каждая запись — непустой уникальный `company_id` и объект `checks`.

Проверки: `identity`, `registry`, `bankruptcy`, `payroll`, `site`, `commute`, `contact`.

Каждая переданная проверка содержит `status` из `pass/fail/review/unknown` и необязательный список `evidence`, отсутствие списка или пустой список превращают результат этой проверки в `unknown`.

Отсутствующая проверка тоже даёт `unknown`, неизвестное имя проверки или неверный формат останавливают весь запуск с кодом 2.

В каждом доказательстве обязательны непустые строки `source` и `scope`, а также `checked_at` и `valid_until`.

`source` — точная ссылка на источник или ссылка на локальный снимок, `scope` — что, где и в каком объёме проверили, а не общая оценка «надёжная компания».

Скрипт проверяет только непустое значение этих строк, доступность снимка, содержимое ссылки и достаточность охвата проверяет человек или содержательный проверяющий.

Сроки строго в UTC `YYYY-MM-DDTHH:MM:SSZ`, без смещения и дробных секунд, `checked_at` должен быть раньше `valid_until`.

Срок актуальности выбирается по изменчивости факта и следующему действию, универсальный TTL скрипт не назначает.

Повторяющиеся ключи JSON, повторяющиеся ID компаний, NaN, Infinity и неверные типы отклоняются, входной файл и переданные объекты не изменяются.

## Решения и срок доказательств

Актуальность каждого приложенного доказательства проверяется по условию `checked_at <= now < valid_until`.

Если хотя бы одно доказательство ещё не действует или уже истекло, статус всей соответствующей проверки становится `unknown`, это относится и к прежним `fail` и `review`.

Истечение доказательства не устанавливает устранение риска, оно требует повторной проверки.

Решение определяется по актуальным статусам в таком порядке:

1. Есть `fail` — `exclude`, положительные проверки и баллы его не компенсируют.
2. Нет `fail`, есть `review` — `review`.
3. Нет предыдущих условий, есть отсутствующее, неподтверждённое или неактуальное — `unknown`.
4. Все требуемые проверки имеют актуальный `pass` — `preliminary` на этапе `api` либо `eligible` на этапе `final`.

`api` оценивает только первые четыре области: identity/registry/bankruptcy/payroll, его `preliminary` означает предварительное прохождение, а не окончательный допуск.

`final` требует всех семи областей, но даже `eligible` означает лишь прохождение формального контроля деклараций, а не содержательное одобрение или разрешение контакта.

Переданные поздние проверки на этапе `api` проверяются на корректность формата, но не участвуют в его решении, это не отменяет уже известный риск и не позволяет обходить итоговую проверку.

Подтверждение identity должно содержательно связывать бренд, сайт и юридическое лицо, отсутствие или неактуальность такого основания не позволяет считать компанию проверенной.

## Выход

```json
{
  "stage": "final",
  "evaluated_at": "2030-01-01T12:00:00Z",
  "companies": [
    {
      "company_id": "synthetic-company",
      "decision": "unknown",
      "checks": {
        "identity": {"status": "pass", "reason": "declared"},
        "registry": {"status": "unknown", "reason": "missing_check"},
        "bankruptcy": {"status": "unknown", "reason": "missing_check"},
        "payroll": {"status": "unknown", "reason": "missing_check"},
        "site": {"status": "unknown", "reason": "missing_check"},
        "commute": {"status": "unknown", "reason": "missing_check"},
        "contact": {"status": "unknown", "reason": "missing_check"}
      }
    }
  ]
}
```

Причины: `declared` — сохранена актуальная декларация, `missing_check` — проверки нет, `missing_evidence` — доказательств нет, `not_current` — срок хотя бы одного доказательства не подходит.

Исходные доказательства не копируются в результат, сохраняй входной файл рядом с отчётом для проверки оснований и не редактируй его задним числом.

Результат не подменяет общий журнал контактов и его блокировки, одна первичная попытка на компанию действует между волнами, ролями, текстами и каналами.
