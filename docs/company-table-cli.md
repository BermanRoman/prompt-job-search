# Постоянная локальная таблица компаний

[company_table.py](../scripts/company_table.py) хранит карточки в той же SQLite-базе `--db`, что и [журнал кампании](../scripts/README.md).

Таблица — первичный источник состояния возможностей, память переписки и ранее показанный HTML её не заменяют.

Скрипт использует только стандартную библиотеку Python 3.9+, сеть и отправку сообщений не реализует.

## Команды

```sh
python3 scripts/company_table.py --db /private/campaign/jobs.sqlite import --input /private/campaign/cards.json
python3 scripts/company_table.py --db /private/campaign/jobs.sqlite status
python3 scripts/company_table.py --db /private/campaign/jobs.sqlite read --company-id synthetic-company --output /private/campaign/company.json
python3 scripts/company_table.py --db /private/campaign/jobs.sqlite export --output /private/campaign/companies.html
python3 -m unittest discover -s tests -p test_company_table.py -v
```

Все команды принимают `--now YYYY-MM-DDTHH:MM:SSZ` для воспроизводимой учебной проверки, по умолчанию используется фактическое текущее UTC.

Для реального решения перед действием не подставляй старое время ради прохождения истёкших проверок.

`import` атомарно применяет пакет, `status` показывает только счётчики, `read` сохраняет одну карточку с версией и новым решением в закрытый JSON, `export` создаёт статическую HTML-таблицу для чтения.

`status --output <новый файл>` дополнительно сохраняет все карточки и решения в закрытый JSON.

Stdout содержит только счётчики, ни адресаты, ни ID компаний, ни заметки туда не выводятся.

База, JSON-входы и результаты должны находиться вне публичного репозитория либо в игнорируемом `runs/`, директории создаются заранее.

База открывается с правами `0600`, символическая ссылка вместо файла базы отклоняется, существующие таблицы журнала не заменяются и не очищаются.

Файлы результатов создаются исключительно с правами `0600`, существующий файл или ссылка не перезаписываются, HTML не содержит скриптов, внешних ресурсов и активных ссылок.

Код выхода 0 означает успешную операцию, 2 — неверный формат, конфликт версии или ошибку хранения, при ошибке импорта весь пакет откатывается.

## Карточка и версии

```json
{
  "companies": [
    {
      "company_id": "synthetic-company",
      "wave": 2,
      "company_name": "Учебная компания",
      "inn": "",
      "city": "Учебный город",
      "website": "https://example.org",
      "workplace": "не подтверждено",
      "role": "Учебная роль",
      "need_hypothesis": "Гипотеза потребности, требуется проверка",
      "recipient": "не определён",
      "contact_source": "",
      "checks": {},
      "expected_version": null
    }
  ]
}
```

Пример намеренно не содержит доказательств, поэтому даёт «НУЖНО УТОЧНИТЬ».

Обязательны `company_id`, `wave`, `checks` и импортное поле `expected_version`.

`company_id` — устойчивый идентификатор одной компании во всех волнах, ролях и каналах, его нужно согласовать с журналом, не создавать новый ID для обхода прежней попытки.

`wave` — целое число 1 или 2, boolean не допускается, порядок волн задан в [company-discovery.md](../company-discovery.md).

`checks` имеет точную схему [company-screen-cli.md](company-screen-cli.md), это осмысленные декларации с источниками и сроками, а не сырой ответ Checko.

Метаданные — строковые поля `company_name`, `inn`, `city`, `website`, `workplace`, `role`, `need_hypothesis`, `recipient`, `contact_source`, `vacancy_url`, их отсутствие допускается для ещё не исследованной карточки.

Непустой `inn` должен состоять ровно из 10 ASCII-цифр, текущая версия поддерживает юридические лица, 12-значные ИНН ИП не поддерживаются.

Без установленного ИНН решение не может быть «ПИШЕМ», даже при семи декларациях `pass`: результат — `clarify/identity_unknown`, если нет более сильного основания «НЕ ПИШЕМ».

Актуальный `fail` и блокировки истории сохраняют приоритет, отсутствие ИНН не смягчает известный стоп-фактор до уточнения.

Один непустой ИНН допускается только у одного `company_id`, псевдонимы из HH и Checko связывай с этой карточкой, не импортируй как новые компании.

Уже установленный ИНН неизменяем: его нельзя удалить, очистить или заменить при правке той же карточки даже с актуальной версией, конфликт останавливает и откатывает весь пакет.

Ошибочную идентичность нужно разбирать отдельно с проверкой связей и истории, автоматического переименования для освобождения антидубля нет.

Отсутствующее или пустое поле означает отсутствие записанного значения, не подтверждение соответствия критерию, подходящая вакансия в `vacancy_url` возвращает возможность в первую волну по методике.

Полные резюме, пароли, ключи API и секреты в таблицу не помещаются, дополнительные поля и повторяющиеся JSON-ключи отклоняются.

`company_cards` содержит `company_id TEXT PRIMARY KEY`, `body TEXT NOT NULL`, `version TEXT NOT NULL`, `updated_at TEXT NOT NULL`.

`body` — канонический JSON карточки без `expected_version`, `version` — SHA-256 UTF-8 представления с сортировкой ключей, без лишних пробелов и с `ensure_ascii=False`, `updated_at` — время последнего изменения UTC.

Для новой карточки передай `expected_version: null`, для изменения существующей — её актуальный SHA-256, полученный через `read`.

Повтор точно такого же содержимого идемпотентен даже при прежнем `expected_version`, изменённое содержимое с устаревшей версией отклоняется без перезаписи.

Это полная замена тела карточки, а не частичное слияние: при правке сохрани известные поля и доказательства, удаление поля станет содержательным изменением.

Повторяющиеся ID в одном пакете отклоняются, история отправок и блокировок при импорте остаётся в таблицах журнала.

При чтении SHA сверяется с телом, ручная подмена содержимого со старым SHA останавливает операцию вместо выдачи допуска.

SQLite — локальное хранилище, а не защищённый от владельца компьютера аудит, содержательно ложную карточку с пересчитанным SHA этот контроль не разоблачает.

## Расчёт «пишем / нет»

На каждом чтении выполняется этап `final` из company_screen по текущему времени и накладывается общая история компании из журнала.

| Условие | Решение | Смысл |
|---|---|---|
| Блокировка компании, отказ либо запрет в любой её opportunity | НЕ ПИШЕМ / `skip` | Новая роль, волна или канал не обходят запрет |
| Есть `reserved` или `unknown` попытка | НЕ ПИШЕМ / `skip` | Сначала выяснить фактический исход, TTL отправки нет |
| Уже есть `sent` | НЕ ПИШЕМ / `skip` | Первичный контакт уже состоялся, дальнейшее возможно только как разрешённая переписка |
| Есть актуальный `fail` | НЕ ПИШЕМ / `skip` | Положительные признаки не компенсируют стоп-фактор |
| ИНН ещё не установлен, других стоп-факторов нет | НУЖНО УТОЧНИТЬ / `clarify` | Декларация identity сама по себе не даёт обойти идентификацию |
| Есть `review`, неизвестное, отсутствующее или истёкшее | НУЖНО УТОЧНИТЬ / `clarify` | Нужны данные либо содержательный разбор |
| Все семь проверок имеют актуальный `pass`, история не блокирует | ПИШЕМ / `write` | Только формальная готовность при дальнейшем ревью и текущем поручении |

Доказанный `not_sent` не считается состоявшейся первичной попыткой, прочие состояния попыток препятствуют новой отправке.

Видимое `last_contact` — последняя по времени создания попытка с состоянием, время резервирования не доказывает доставку или прочтение.

HTML показывает решение и причину в первых колонках, русские подписи, метаданные, отдельные семь проверок, последнее состояние контакта и исходные источники с датами в раскрываемом блоке строки.

Для широкой таблицы предусмотрены горизонтальная прокрутка, закреплённая шапка и перенос длинного текста, доказательства раскрываются встроенным HTML-элементом без JavaScript.

HTML — снимок расчёта при экспорте, перед действием пересчитай состояние в базе, не принимай старую страницу за актуальный допуск.

## Интерфейс для журнала

`decision(connection, company_id, now)` возвращает словарь с `decision: write|skip|clarify`, `reason`, `company_id`, `screening` и `last_contact`.

Функция не открывает и не завершает транзакцию, не меняет данные и ничего не печатает, журнал может вызывать её внутри своего `BEGIN IMMEDIATE` перед резервированием.

Отсутствие карточки даёт `clarify/missing_card`, отсутствие ещё не созданных таблиц журнала допустимо, повреждённая карточка вызывает ошибку и не даёт продолжать отправку.

Изменение версии карточки должно отзывать прежнее одобрение пакета через проверку `company_version` в журнале, итог `write` не заменяет проверку байтов, полномочий и лимитов.

Если используется `import_cards` напрямую как библиотечная функция, вызывающая сторона обязана обеспечить транзакцию и откат пакета при ошибке, CLI делает это самостоятельно.
